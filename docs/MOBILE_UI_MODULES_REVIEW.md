# 모바일 UI 모듈(AppHeader, BottomNavBar) 개선 제안 및 기술 검토

본 문서는 현재 리팩토링된 `AppHeader` 및 `BottomNavBar` 모듈의 품질, DX, 성능, 확장성 측면을 비판적으로 검토하고 향후 개선 방향을 제시합니다.

---

## 1. 코드 품질 (Code Quality)

### 긍정적인 점

- **컴포지션 패턴(Compound Pattern)** 도입으로 내부 코드 수정 없이 외부에서 레이아웃을 완전히 재구성할 수 있습니다.
- **관심사 분리**: 스타일(Tailwind), 타입, 비즈니스 로직(Control)이 물리적인 파일로 잘 분리되어 있습니다.
- **우선순위 로직**: Props(명시적 선언)와 Context(동적 상태)의 우선순위를 정해두어 유연한 사용이 가능합니다.

### 비판적 개선점

- **순수성 결여**: `AppHeader` 내부에서 `useSession`, `signOut`, `router.back()` 등 특정 라이브러리(`next-auth`, `next/navigation`)에 직접 의존하고 있습니다. 이는 모듈을 다른 프로젝트로 가져갈 때 수정이 필요함을 의미합니다.
- **동질성 부족**: `AppHeader`는 컴포지션 패턴을 지원하지만, `BottomNavBar`는 아직 리스트 주입 방식에 머물러 있습니다. 구조적 통일이 필요합니다.

---

## 2. 개발 경험 (Developer Experience)

### 긍정적인 점

- **`useHeader`, `useBottomNav` 훅**: 레이아웃 구조를 변경하지 않고 페이지 내부 로직만으로 UI를 제어할 수 있어 페이지 개발 생산성이 높습니다.
- **Convenience Props**: 복잡한 설정 없이 `title="제목"` 만으로도 기본 동작이 보장됩니다.

### 비판적 개선점

- **상태 오염(State Leakage)**: 페이지가 바뀔 때 `resetHeader`가 자동으로 호출되지 않으면 이전 페이지의 설정이 다음 페이지에 남아 있는 문제가 발생할 수 있습니다.
- **타입 복잡도**: `Object.assign`을 사용한 패턴은 IDE 인텔리센스에서 가끔 복잡하게 노출될 수 있습니다.

---

## 3. 성능 (Performance)

### 비판적 개선점

- **불필요한 리렌더링**: `useHeader`는 `useEffect`를 통해 상태를 업데이트합니다. 만약 호출하는 쪽에서 객체나 함수(`onBack`)를 메모이제이션(`useCallback`)하지 않고 넘긴다면, 매 렌더링마다 전역 상태를 업데이트하게 되어 성능 저하를 유발합니다.
- **Client-Side Heavy**: 레이아웃 전체가 `"use client"`가 되면서 서버 사이드 렌더링(SSR)의 이점이 줄어듭니다. (헤더/네이게이션 자체는 클라이언트가 맞지만, 그 아래 정적 콘텐츠까지 영향을 미칠 수 있음)

---

## 4. 확장성 및 지속 가능성 (Scalability & Sustainability)

### 개선이 필요한 점

- **애니메이션 레이어 부재**: 헤더 타이틀이 바뀌거나 하단 바가 숨겨질 때 부드러운 트랜지션 처리가 되어 있지 않습니다. `Framer Motion` 등과 결합할 수 있는 인터페이스가 필요합니다.
- **배지(Badge) 및 알림**: `BottomNavBar` 아이템에 새 알림 수(Badge)를 표시하는 기능이 추가될 때, 현재 구조는 `NavItem` 타입을 계속 확장해야 하는 구조입니다. (이것도 컴포지션 패턴으로 가야 함)

---

## 5. 최종 제안 및 Action Plan

### 🚀 단기적 개선 (Immediate)

1. **메모이제이션 가이드라인**: `onBack` 등 함수를 넘길 때 `useCallback` 사용을 강제하거나 내부적으로 최적화 처리.
2. **자동 상태 리셋**: `useHeader` 내부적으로 `unmount` 시점에 상태를 초기화하는 안정 장치 추가.

### 🏗️ 장기적 개선 (Structural)

1. **Dependency Injection**: 로그아웃 로직이나 뒤로가기 로직을 모듈이 직접 들고 있지 않고, 외부에서 주입받는 인터페이스로 변경 (완벽한 프로젝트 독립성 확보).
2. **Portals 활용**: 레이아웃이 아닌 실제 페이지 컴포넌트 내부에서 헤더 영역으로 HTML을 쏴주는 `Portal` 방식을 도입하여 SSR 이점과 동적 장악력을 동시에 확보.
3. **BottomNavBar 고도화**: 하단 바도 `BottomNavBar.Item`과 같은 컴포지션 패턴으로 변경하여 배지 표시나 특별한 애니메이션 아이템을 자유롭게 추가 가능하도록 수정.

---

**결론**: 현재 구조는 초기 개발 속도와 유연성 사이에서 훌륭한 균형을 잡고 있으나, 서비스가 커질수록 **상태 관리 최적화**와 **서드파티 라이브러리 의존성 분리**가 핵심 과제가 될 것입니다.
